> 原文逐字见《落地策略_原文存档.md》。
> 这份文档只做三件事：把混用的词定死；把只有方向、没有判据的条目补成「怎么算做到」；把彼此拉扯的地方说明白。

## 〇、一句话

把《人机协同编程方法论》从**一篇把道理讲清楚的文章**，变成**一份装进任何项目、人和 AI 都照着执行的操作手册**。

两者的分工要固定下来：方法论回答「为什么这么做」，落地策略回答「装在哪、长什么样、怎么验收」。任何一句话如果两边都写，迟早会不一致。

---

## 一、先定词

原文里「法则 / 规则 / 规范 / 机制」混用，指代并不一致。不先拆开，后面四项核心工作会互相打架。

| 词 | 本文含义 | 判别方法 |
|---|---|---|
| 方法论 | 三阶段、四环、五信号这套道理 | 不可执行，只解释 |
| 机制 | 可复制到任意项目的一套文件 + 脚本 + 适配层 | 整目录复制后仍可用 |
| 规则 | 一条一行、祈使句、不写论证的约束，形态照主流 IDE 规则 | 两个人独立判定，结论一致 |
| 指标 | 带阈值、可采集的数值约束 | 一条命令能出数 |
| 规范 | 文档的格式要求 | 缺字段即不合规 |
| 操作手册 | 给人看的执行序列 | 新人照做能走完一次迭代 |

三点补充说明：

- 「法则」在原文里同时指「规则」和「方法论」，我按上下文分别归入这两类，不再单列。
- 「落地原则」里的「原则」是**对机制本身的约束**，和规则三层次里的「原则层」不是一回事。下文提到层次时一律写「原则层」，避免撞词。
- 「规则」的形状就按主流 IDE 规则来：`AGENTS.md`、规则目录里那种一条一行、祈使句、不写论证的写法。但形状是给读者看的，判据是给判定用的，两者都要，见 §三.1。

## 二、四条落地原则

### 1. 脱离仓库

原话：脱离仓库、能装到任何项目上的机制。

中译中：**机制是货，仓库是货架。货不能长在货架上。**

判据，三条全过才算做到：

- 整个目录复制到另一个仓库，不改内容即可用；
- 唯一允许改的是项目名、路径、语言工具链这类**配置**，不是规则文本；
- 本仓库只是**第一个使用者**，不是机制的宿主。

由此推出一条隐含禁令：**规则里不许出现本仓库的专有约定。** 一旦出现 `packages/`、`src/lib` 这种目录名，它就已经不是可移植机制，而是项目规则。两者必须分开放——机制层写「什么算合格」，项目层写「这个项目里合格长什么样」。

### 2. 交付物是规范 + 操作手册

原话：落地结果：用户可以根据规范【操作手册】实现人机协同共同完成开发任务。

中译中：**验收标准不是「文档写全了」，而是「别人照着做完了」。**

- **规范**是约束：什么算合格、什么不许做。
- **操作手册**是序列：先做什么、再做什么、每步的输入产出和退路。
- 交付结果 = 这两样，加上让它们能被执行的检测脚本。

判据：

- 一个没读过方法论的人，只读操作手册，能完成一次「需求 → 契约 → 代码 → 门禁通过」的闭环；
- 手册每一步都写清：谁做、输入是什么、产出是什么、怎么算做完、做错了退到哪；
- 手册不解释道理，需要解释的地方直接链回方法论。

### 3. 适配主流 IDE

原话：法则应该适配主流的ide工具（能被各种ide识别并使用）；通用的agent协议？

中译中：**不要押注某个「通用协议」，要押注「单一事实源 + 适配层」。**

现状是：并不存在被所有 IDE 共同实现的 agent 协议，事实上的公约数只有 `AGENTS.md`（多数工具会把它当作项目级指令入口），其余工具各有各的入口文件。因此结构只能是：

- **事实源一份**：`AGENTS.md` 加上规则、指标、手册正文。只有一份，任何地方都不复制。
- **适配层多份**：各 IDE 的入口文件只写「先读哪些文件、冲突以谁为准」，不承载规则内容。
- **判据**：任选一个 IDE 打开仓库，AI 都能在不靠用户粘贴的前提下读到同一份规则；改规则只需要改一处。

反过来说：**一条规则如果需要在两个入口各写一遍，它就已经失效了**——两份迟早不一致，而不一致时 AI 会挑看起来更近的那份执行。

### 4. 功能区与法则区分开放

原话：功能区则属于常规文档（常规项目文件）。

中译中：**这条的重点不是「用 Markdown」，而是「和法则分开」。** 功能区放功能文档（需求、契约），法则区放法则文件（规则、指标、手册、技能、脚本），两边各自成根，互不混放。

最常见的错法是把两者写进同一份文件：上半段是「本模块必须如何如何」，下半段是「本次要加什么功能」。这种文件两种身份都占，结果两种用途都不能用——法则没法整体复制，功能文档也没法按次封存。

判据：

- **可移植性试纸**：法则目录整份复制到另一个仓库仍然成立；功能文档复制过去无意义。混在一起时，整份复制会连同项目需求一起搬走，一试就露。
- **变更独立性**：改一次需求不需要动法则目录；改一条规则不需要动功能文档。
- **单一归属**：任何一份文件只属于一个区，不存在「既是规则又是需求」的混合文档。

至于「常规文件」本身，仍是硬要求：Git 可 diff、可 review、可回溯；不装任何工具也能读、能改、能人工执行检查；不依赖平台账号、数据库、看板。它的作用是**降低采用成本**——一套要先装服务的流程，没有小项目会用；而没人用的流程，写得再对也等于零。

## 三、四项核心工作

先给边界，再给验收。四项不是并列的四件事，而是有先后依赖的四个层，顺序见第五节。

### 1. 规则的内容与编排

原文「法则规则具体内容和内容」重复了「内容」，我读成两件事：**写哪些规则**，和**怎么组织它们**。

#### 规则写成什么样

规则的形态就照主流 IDE 规则来：一条一行、祈使句、只写约束不写论证，放在 AI 一进仓库就能读到的地方（`AGENTS.md`、规则目录）。理由很实在——这种写法 AI 最容易照做，也最容易被 lint 类工具接住。

但**「像 IDE 规则」不等于「免于可判定」**。形态是给读者看的，判据是给判定用的。你给的判定表说的就是这件事：

| 写法 | 判定 | 原因 |
|---|---|---|
| 代码要干净 | 不是规则 | 无判据，两个人结论必不一致 |
| 模块间低耦合、高内聚，兼顾性能 | 不是规则 | 三个命题 + 三个模糊词 |
| 禁止跨包引用内部实现路径 | 是规则 | 给定代码树可机械判定，有明确反例 |
| 每个公开 HTTP 错误响应必须含 code 字段，取值属于枚举 E | 是规则 | 有限枚举，可脚本校验 |

两条推论，直接写进立法流程：

- **形容词不进规则。**「干净」「优雅」「合理」「性能好」只能出现在原则层，由人裁量。
- **复合命题必须拆。** 一句话里出现「以及 / 同时 / 兼顾」，先拆成几条；拆完仍无判据的，降级。

#### 一张卡 = 一条规则

字段固定为：ID / 一句话约束 / 层级（原则层·规则·指标）/ 可判定判据 / 执行者（人·工具）/ 违反代价 / 门禁级别（提示·阻断）/ 首次立法原因。

#### 编排：三层分开放

原则层只由人裁量；规则必须可判定；指标必须可测量。混写的后果，就是方法论里指出的那对假矛盾——「规则靠 AI 主观理解」和「规则要语义明确」互相拆台。

#### 验收

两个人拿同一份产出、同一张卡，独立判定，结论一致。不一致的卡，退回原则层，不许留在规则里冒充可执行。

### 2. 指标的范围、阈值与采集工具

原文只提了三项，我补齐成五要素，缺一不成立：

| 要素 | 说明 | 缺了会怎样 |
|---|---|---|
| 范围 | 首批只选能被脚本算出来的 | 选多了人会被拦在门外 |
| 阈值 | 三段：基线（只记录）→ 警告（提示）→ 阻断（失败） | 一上来就阻断，流程第一天就没人用 |
| 采集工具 | 一条命令出数，零依赖优先 | 采不到，指标就是愿望 |
| 趋势 | 每次采集追加一行历史，能看出劣化 | 只有当前值，退化发现不了 |
| 归属 | 哪个阶段产生、谁负责修 | 指标红了没人认领，等于没有 |

- **验收：一条命令同时产出「当前值 + 阈值判定 + 追加一行历史」。**
- **阈值不靠拍脑袋：先只记录跑一段时间，用真实分布定线，再升级为警告和阻断。** 这是唯一能避免「上线即误拦」的做法。

### 3. 语义立约的格式与内容

原文点了两份文档，但没给格式。补成两类，职责不同：

- **需求文档 = 时间轴上的一次变更。** 一次诉求一份，定稿后封存，永不修改。
  必备章节：场景 / 目标 / 非目标 / 边界（明确不要什么）/ 验收判据 / 反例 / 开放问题。
- **契约文档 = 系统当前状态的截面。** 始终只有一份最新版，随迭代改动其中若干条，不堆积历史。
  必备字段（按实体）：名称 / 归属 / 输入输出 / 错误语义 / 不变量 / 调用前提 / **尚未实现但必须遵守的承诺**。

「语义立约」的收工标准只有一条：**实现者读完契约，不需要再问任何问题。**

反例判据：如果契约里每一条都能在现有代码里找到对应，它只是把代码翻译成了中文，没有约束力。

### 4. 代码交付与检测流程

原文说「交付和检测」，但没说检测什么。这里定死：

- **检测对象只有两个**：实现是否与契约逐条相等、门禁是否通过。代码风格属于规则，不归这里管。
- **流程四环**：立法 → 执法 → 度量 → 回归。缺执法，规则是标语；缺度量，劣化看不见；缺回归，修一个坏三个。
- **三机制保证「严格对应」**：契约生成骨架（正向）、实现暴露面与契约逐条核对（反向）、改契约不改代码则门禁失败（同步）。
- **收工定义**：反向核对通过 + 门禁全绿 + 指标已记录 + 文档已回写。四样缺一，不算交付。

## 四、五处张力，以及我解开的方式

1. **「脱离仓库」 vs 「需要脚本执行」。**
   脚本必须零依赖、可降级：有 Node 用 Node，没有就用 shell，再没有就输出人工检查单。机制不能因为环境缺东西就整条失效。
2. **「通用协议」 vs 现实。**
   协议不存在，就把协议降级成转发层。见原则 3：事实源一份，适配层只转发。
3. **「操作手册给人看」 vs 「人类不审代码细节」。**
   手册必须分角色段落：人读的部分只出现裁决、边界、验收；AI 读的部分才出现命令和文件路径。混写会把人重新拖回代码评审，那正是方法论里最贵的一种花法。
4. **「能装到任何项目」 vs 「指标依赖语言工具链」。**
   指标分两层：语言无关层（契约一致性、文档漂移、归属完整性）先上；语言相关层（复杂度、覆盖率、lint）按项目选装。
5. **「IDE 规则写法」 vs 「可判定」。**
   IDE 规则的惯常写法偏向表态（「保持简洁」「注意性能」），而机制要求每条都能判定。解法是拆开看：**形态照 IDE 写，判据照规则卡补**。补不出判据的，不删，降级进原则层——它仍然有用，只是不能冒充门禁依据。

## 五、落地顺序

这不是排期，是依赖关系：

**规则（可判定）→ 契约格式（有形状）→ 反向核对脚本（能对比）→ 指标阈值（有数据）→ 操作手册定稿（把前四步串成序列）。**

理由很直接：没有可判定的规则，契约写不出形状；没有契约，一致性指标没有比较对象；没有指标数据，阈值只能拍脑袋；没有前四步，手册只是目录。
