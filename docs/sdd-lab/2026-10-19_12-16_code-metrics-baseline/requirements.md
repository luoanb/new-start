# Requirements / 需求文档: 客观代码度量基建

## Restated Understanding / 需求复述

- 我理解当前需求是：为代码库建立一套可复现、可追溯的客观度量基建，先建立可信基线，再补充形成重构证据所需的数据。
- 当前核心目标是：忠实记录数据与确定性计算结果，不由系统代替用户作质量判断或重构决策。
- 当前边界是：完成两个阶段的本地采集、统一 JSON、聚合报告、Git/复杂度/重复/依赖证据，以及可选的用户配置评价层。
- 暂不处理：CI 阻断、质量阈值、默认热点权重、默认重构候选、长期趋势平台和可视化看板。

## Scope / 范围

### In

- 第一阶段：定义指标口径，明确源码、测试、生成/派生内容和排除目录。
- 第一阶段：支持 tracked 与 worktree 两种明确标识的文件集合。
- 第一阶段：输出带版本的统一 JSON，以及仅由 JSON 派生的 Markdown 摘要。
- 第一阶段：按仓库、分类、workspace、目录和扩展名聚合，并计算明确算法的分位数。
- 第一阶段：固化 Node、pnpm、命令、配置哈希、Git 状态和路径/换行规则。
- 第二阶段：采集 Git 修改次数、added、deleted、churn、贡献者和历史覆盖区间。
- 第二阶段：采集 TypeScript/Svelte 圈复杂度、重复代码和循环依赖事实。
- 第二阶段：输出每个文件的事实向量、独立排名和分位位置。
- 增补（2026-10-26）：把重复片段 pair 聚合为「重复簇」，输出每个簇的重复次数；归并参数（重合度口径、阈值）可配置，默认口径为交叠行数 ÷ 较短区间长度，默认阈值 0.6。
- 第二阶段：提供默认关闭的可配置热点公式和候选筛选器；只说明命中的用户规则和事实值。
- 新基建建立后删除 `scripts/count-lines.mjs`，不保留旧命令兼容层。
- 增补（2026-10-26）：补齐已承诺但未闭环的契约：运行时报告校验、工具版本、采集覆盖与失败原因、CLI 退出码、HEAD 提交时间相对的 Git 窗口、重命名策略、mailmap/显式身份映射、强连通分量。
- 增补（2026-10-26）：增加五项结构性事实：认知复杂度、唯一重复行与重复密度、依赖稳定度、时间耦合。这些值仍只描述结构或历史，不解释为质量。

### Out

- 不把行数、复杂度、修改频率或综合分直接解释为代码质量。
- 不自动输出“应该重构”“高风险”“低质量”等判断。
- 不提供默认综合权重、默认候选阈值或默认质量门禁。
- 不把测试覆盖率、构建耗时、包体积和线上缺陷纳入本次两个阶段。
- 不在本次接入 GitLab CI，不阻断提交、合并或发布。
- 不建设长期指标数据库、趋势看板或跨仓库对比。

## User Interaction / 用户交互

- 触发入口：根目录 pnpm scripts。
- 用户操作路径：选择 baseline、evidence 或 all 命令，可显式指定配置、文件集合和输出目录。
- 系统反馈：生成机器可读事实 JSON、派生报告 JSON 和 Markdown 摘要，并列出采集覆盖率与错误原因。执行过程向 stderr 输出阶段进度；进度文本不进入 JSON。
- 状态变化：每次执行产生独立快照，不修改业务源码，不自动覆盖用户保存的历史基线。
- 异常/边界交互：无法解析、历史不足、二进制、身份无法归一等情况输出 `null` 或独立状态及原因。
- 不应发生的交互：静默补零、隐藏失败文件、使用未声明权重、根据分数直接给出重构结论。

## Acceptance Criteria / 验收标准

- [ ] 同一 commit、配置和工具版本重复运行时，除采集时间与耗时外，JSON 内容一致且顺序稳定。Git 时间窗相对 HEAD 的提交时间计算，不使用采集时的墙钟。
- [x] 每项数值都可追溯到采集口径、工具版本、配置和对应原始事实。
- [ ] tracked 与 worktree 口径明确区分，dirty 状态被记录。
- [ ] 生产源码、测试、demo、i18n、图标组件、API 类型、资源、文档、工具链和派生产物可独立分类。
- [ ] 总行数、非空行数、字节数和文件数使用准确名称，不将非空行误称为 SLOC。
- [ ] 聚合结果包含样本数和固定算法的 P50/P75/P90/P95/P99。
- [ ] 重复簇的重复次数 = 簇内区间实例数；同文件自我重复计为不同实例；每个簇可追溯到全部成员 pair。
- [ ] 重复簇归并的重合度口径与阈值写入配置并参与配置哈希；默认值为「较短区间 / 0.6」。
- [ ] Git 输出包含实际历史起点和覆盖天数；历史不足时不伪装成完整时间窗。
- [x] 复杂度、重复和依赖采集均报告成功覆盖率、失败项和失败原因。
- [x] 未配置评价规则时不生成热点综合分或重构候选。
- [x] 配置评价规则后，输出完整公式/参数、参与字段、缺失值策略和逐文件命中依据。分数写入每个命中文件；不生成仓库级单一综合分。
- [x] `scripts/count-lines.mjs` 在新入口覆盖第一阶段能力后被删除。
- [x] 报告输出循环依赖的强连通分量，并保留去重后的环路径。
- [x] 认知复杂度按本文固定的 Sonar 子集计算；嵌套函数独立计分。
- [x] 唯一重复行先合并同一文件内的闭区间，重复密度 = 唯一重复行 / 有行数文件的总行数。
- [x] 依赖稳定度 = 唯一出度 /（唯一入度 + 唯一出度），分母为 0 时为 null。
- [x] 时间耦合输出共同提交数、双向条件概率和 Jaccard，并记录窗口与最小次数。

## Constraints / 约束

- 业务约束：主观判断归用户所有，系统只提供事实和用户显式配置的计算结果。
- 技术约束：适配当前 pnpm monorepo、TypeScript 5.9、Svelte 5、Windows 路径及现有 Git 历史。
- 技术约束：JSON 是报告真相源。`facts.json` 只保存原始记录；`report.json` 只保存元数据、派生结果、评价和诊断，不再内嵌 `facts`。同一数值只保存一次。Markdown 从这两份 JSON 读取，不另写一套数。
- 技术约束：原始事实、确定性派生和用户评价必须在 Schema 中分层。
- 兼容性约束：不保留 `scripts/count-lines.mjs` 的 CLI 兼容层。
- 流程约束：文档批准前不进入代码、配置或依赖修改。

- 2026-10-26 10:45:
  - 决策：重复簇归并的重合度口径与阈值均做成配置参数；默认口径为交叠行数 ÷ 较短区间长度，默认阈值 0.6。
  - 原因：探针实验（`.artifacts/code-metrics/_probe-dup-cluster.cjs`，1005 条真实 pair）显示阈值在 0.5–1.0 区间对结果几乎不敏感，口径分母才是有实质影响的参数；「较短区间」口径使 jscpd 报出的嵌套子 clone 归并入母簇，同一处重复不打散。
- 2026-10-26 11:11:
  - 决策：重复簇按「重复体量 = 重复次数 × 最大区间行数」降序输出，不按单纯重复次数排序。
  - 原因：小片段大量复制与大片代码少量复制需要同一把尺子衡量；只按次数排序会把高体量的巨型复制块埋在长尾。
- 2026-10-26 16:54:
  - 决策：补齐当前契约缺口，并把认知复杂度、唯一重复密度、强连通分量、依赖稳定度和时间耦合纳入事实层。
  - 原因：用户要求补充第一优先级指标，并兑现 SDD 中已承诺但尚未完整实现的能力。
  - 决策：`evidence` 与 `all` 都执行完整采集。二者是同一算法的两个入口，不表示不同口径。
  - 决策：评价分数只按命中文件输出。仓库级 `evaluation.score` 保持 null。
  - 决策：Git 的 90/180 天窗口以 HEAD 提交时间为终点，保证同一 commit 不随采集日期变化。
- 2026-10-26 17:58:
  - 决策：原始记录只进入 `facts.json`。函数明细是复杂度的唯一存放处；重复片段只进入重复总表；依赖只进入图。文件上的汇总数字和排名里的 `value` 不再保存。`report.json` 只保留 `meta`、`scope`、`derived`、`evaluation`、`diagnostics`。
