一句话：插件之间是**契约关系**，不是调用关系。它们彼此不 import，只通过五种契约连接。

| 关系 | 方向 | 耦合度 | 失败模式 |
| --- | --- | --- | --- |
| 服务依赖（inject） | 消费者 → 提供者 | 强 | 缺服务则插件保持 PENDING，不启动 |
| 事件 | 发布者 ↔ 订阅者 | 弱 | 无订阅者时静默丢弃 |
| UI 槽位（Slots） | 贡献者 → 槽位所有者 | 中 | 槽未声明则不渲染并告警 |
| RPC | Client 插件 → Host 方法 | 中 | 方法不存在返回 500 |
| profile 覆盖 | 后层 → 前层 | 装配期 | 同 id 整条替换 |
| 生命周期 | 父 fiber → 子 fiber | 结构性 | 提供者卸载会级联消费者 |

## 1. 服务依赖：能力契约

提供者用 `ctx.provide` 注册一个具名能力，消费者在 `inject` 里声明需要它。双方只认服务名，不认实现包。

- 提供者不知道谁在消费，可以整体替换实现。
- 同一作用域内**同名服务只能有一个**，重复注册直接抛错（`service "x" has been registered at ...`）。
- 依赖是动态的：提供者卸载后，依赖它的插件会被 Cordis 置为 PENDING，而不是继续拿着失效引用跑。

这是插件间最强的耦合，也是唯一应该承载“能力依赖”的关系。

## 2. 事件：通知契约

发布者只管 `emit`，订阅者只管 `on`，两边互不知道对方是谁。适合“发生了变化”这类事实，不适合“请你给我一个结果”。

- 一对多，天然解耦。
- 无人订阅时静默丢弃，所以不能把事件当可靠队列。
- 名字是字符串，拼错不会报错，只能靠命名约定（建议 `<plugin>/<fact>`）。

## 3. 槽位：UI 组合契约

槽位所有者声明“这里有一个洞”（`children`），其他插件往洞里填组件。

- 所有者不知道谁会填，贡献者也不需要知道还有谁。
- 一个槽可以多个贡献者，用 `order` 排序、`id` 去重。
- 父组件卸载时，子槽整体消失；当前实现只在启动时校验孤立注册，运行期动态卸载不会重新校验。

这条关系的关键是**声明即授权**：没被声明的槽，贡献者塞不进去。

## 4. RPC：跨端调用契约

Client 插件按方法名调用 Host 方法，注册方和调用方只共享方法名与 JSON 结构。

- 方法名是全局命名空间，重复注册直接抛错，所以必须带插件前缀（`hello.greet`）。
- 调用是点对点的，调用方必须知道方法存在；这比事件耦合强，但比 import 弱。
- 被调用插件禁用后，方法立即消失，调用方拿到 500。

## 5. 装配覆盖：配置契约

profile 的分层不是“插件互相修改”，而是“后层覆盖前层”：

- 同 id 后出现的层**整条替换**前面的条目。
- 这允许 profile 覆盖 bundle 的配置，但不允许 A 插件运行时改 B 插件的代码。

## 6. 生命周期耦合

结构上所有插件都是同一棵 Cordis fiber 树的节点：

- 根插件卸载 → 所有子插件级联卸载。
- 服务提供者卸载 → 消费者被置为 PENDING。
- 槽位所有者卸载 → 其子槽贡献不再渲染。
- 当前 Host 只支持根级平行挂载，没有插件嵌套挂载与 realm 隔离。

## 当前实现里“强制”与“约定”的边界

| 规则 | 状态 |
| --- | --- |
| 重复服务 / 重复 RPC / 重复 slot id 报错 | 强制 |
| 服务缺失则 PENDING | 强制（Cordis） |
| 槽未声明则告警 | 强制（启动期） |
| 插件之间不得互相 import | **仅约定**，未做依赖图校验 |
| 事件命名规范 | 仅约定 |

最后一条是后续要补的：如果要认真做插件生态，应该像 dsh 那样加一条“feature 插件不得运行时引用另一个 feature 插件”的校验，否则解耦会退化成隐式 import 网。

**设计建议**：能力依赖用服务，状态变化用事件，UI 扩展用槽位，跨端调用用 RPC，装配差异用 profile。四条边界不要互相替代。
