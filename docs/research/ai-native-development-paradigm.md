# 编程新范式：面向 AI 协作的可审计构建方法论

> 课题：在人机协作开发中，如何让一个人稳定操作 10~100 个 AI
> 结构：立法（稳定区）+ 需求迭代（功能区），两者独立演进
> 术语：语义立约（人）+ 代码交付（AI）
> 状态：草案（方法论提案）

---

## 一、总纲：两套独立系统

传统开发中，人写代码，语义立约与代码交付都发生在写的人脑子里：生产成本高，审计成本低。

AI 协作中，代码交付交给 AI，人只保留语义立约：生产成本趋零，但审计对象变了——人不再读实现，而是判断交付的代码是否忠于语义契约。若仍要求逐行审计，AI 只是把打字成本转移成阅读成本；而生成速率远大于阅读速率，待审队列会无界增长。

### 语义立约与代码交付，不要混为一谈

| | 语义立约 | 代码交付 |
|---|---|---|
| 对象 | 问题域、需求 | 解空间、代码 |
| 产出 | 语义契约：实体、状态、不变量、边界、验收条件 | 代码与证据：数据结构、控制流、模块划分、错误处理 |
| 传统开发 | 人（常隐含在脑中） | 人 |
| 新范式 | 人 + AI，人是审核者 | AI |
| 决定 | 做什么、什么算对 | 怎么做 |
| 审计方式 | 人审语义 | 机器验证 + 证据 |

传统开发中，同一个人同时完成这两件事，所以「想清楚」和「写正确」混在一起。新范式把代码交付剥离给 AI，把语义立约显式化为人机接口。因此准确的说法是：**人没有参与代码交付，但深度参与了语义立约**。语义契约如果不可判定，人既没有代码交付的细节知识、也没有可验证的语义契约，审计成本才会真正失控。

新范式的第一刀，不是切代码，而是把系统切成两套**互不依赖**的机制：

| | 立法（稳定区） | 需求迭代（功能区） |
|---|---|---|
| 目标 | 保证代码可控 | 保证本次需求落地 |
| 对象 | 代码库本身 | 一次需求 |
| 问题 | 「这套代码还允许这样长吗？」 | 「这次要做的东西做对了吗？」 |
| 产出物 | 概念、契约、规则、预算 | 语义契约 + 代码交付物 |
| 生命周期 | 长期，跨需求 | 单次，交付即归档 |
| 变更权 | 人（独立立法流程） | 人 + AI（迭代内） |
| 失败表现 | 代码失控：不可审、不可并行、腐化 | 做错东西：实现与意图不符 |

### 独立性是硬约束

两区**不互相引用、不互相转化**：

- 立法不引用任何一份需求文档。一旦法条里写进了某个具体需求，它就会随需求频繁变更，稳定区随之瓦解。
- 需求文档不承担立法职责。它只描述本次要做什么，交付后归档，不沉淀为长期概念。
- 需求迭代过程中不得顺手改法。确实撞上立法边界时，停下来，转入独立的立法流程判断，而不是在迭代里就地修改。

### 唯一交点是代码

两者从不同方向约束同一个东西：

```text
立法（横切）：约束所有代码的形状
════════════════════════════════════
需求 A      │ 需求 B      │ 需求 C     ← 纵切：每次交付
────────────┼─────────────┼───────────
代码 A      │ 代码 B      │ 代码 C
```

- **立法是横切**：定义代码允许长成什么样，对所有需求一视同仁。
- **需求是纵切**：定义这一次要交付什么，只对本次负责。
- 两者在代码处相遇，但验收分开做：立法看规则与指标，需求看语义契约与验收条件。

分离的意义只有一条：**防止互相污染**。需求污染立法，法条会膨胀；立法污染需求，文档会变成八股。两者都独立，才能一个长期稳定、一个快速迭代。

## 二、立法（稳定区）：保证代码可控

### 2.1 目标是「可控」，不是「正确」

立法不回答「做什么」，只回答「代码允许长成什么样」。可控可以拆成五个可检验的维度：

| 维度 | 含义 | 检验方式 |
|---|---|---|
| 可读 | 人能在概念级定位问题 | 概念台账是否完整 |
| 可测 | 契约可以被机器验证 | 不变量是否有对应测试 |
| 可替换 | 边界清晰，实现可换 | 依赖方向是否单向 |
| 可并行 | 无隐式共享面 | 同一概念是否被多处改 |
| 可回滚 | 变更相互隔离 | 单个改动的爆炸半径 |

### 2.2 数据驱动（指标驱动）

关键不在「采集」，而在「限制」。

- **采集**解决「看得见」，**限制**解决「不许退化」。只采集不限制，指标就是报表装饰；只限制不采集，限制就是拍脑袋。
- **指标不等于数据**。数据是原料，指标是有基线、有方向、有阈值、有归属的量。
- **无主指标不采集**。无法归因到唯一实体的指标，不能驱动任何行动。
- 指标限制还有一层作用：**限制上报给人的信息量**。正常执行静默，越界才上报。

### 2.3 规则驱动

关键不在「有规则」，而在「规则可执行」。

- 规则的第一价值不是「正确」，而是**稳定与可审计**：同输入同输出，出错能定位到是哪条规则拦住的。
- 写在 wiki 里的规范等于没有规范。只有类型、lint、依赖方向、状态机约束、schema 版本、CI 门禁这类「不遵守就跑不过」的东西才算规则。
- 规则有生命周期：owner、命中记录、退役条件。没有指标证明仍在生效的规则，视为已死。

### 2.4 语义明确，边界清晰

这是地基，不是第三条。

- **不允许离散代码**。离散代码指没有归属、没有名字、没有契约的代码：魔法数字、一次性脚本、复制粘贴的片段、字符串当状态、跨层直连。它既无法被规则约束，也无法被指标归因，必然腐化——是系统里的暗物质。
- **每个实体都要有语义概念**。代码的最小单位是概念，不是函数或文件。命名即定义；叫不出名字，说明还没想清楚，那就不该写。
- **砌砖，不堆沙**。区别不在是否模块化，而在每个单元是否被迫遵守同一套契约，因此组合结果可预测。砖形状统一、接口明确、可承重、可替换；沙无定形，靠胶水勉强成形，一动就塌。
- **准确是前提，简要是结果**。不准确的简要叫含糊，它不会消灭审计成本，只会把成本藏起来。

### 2.5 立法的产物

| 产物 | 内容 | 作用 |
|---|---|---|
| 概念台账 | 每个概念一张概念卡 | 定义代码由哪些实体组成 |
| 契约三件套 | 类型/接口、不变量、依赖规则 | 定义实体之间允许怎样组合 |
| 可执行规则 | 类型、lint、门禁、schema 版本 | 让违约跑不过 |
| 三本预算 | 质量、结构、注意力 | 定义是否正在退化 |

### 2.6 立法的门槛与节奏

- 只立与具体需求无关、对全体代码生效的法。
- 判据：一条法如果不能用一条规则或一个指标表达，它还不是法，只是愿望。
- 法越少越稳。法条膨胀本身就是失控的一种形式。
- 每条法都要有 owner、命中记录、退役条件。
- 立法有自己的节奏：由可控性信号（指标越界、事故、审计成本上升）驱动，而不是由需求上线驱动。

## 三、需求迭代（功能区）：只服务本次交付

### 3.1 语义立约：人机对接的唯一资料

语义契约是人与 AI 之间唯一的对接资料。它比自然语言精确，比代码简洁，是「意图」与「实现」之间的合同——但它是一份**只对本次需求生效的合同**。

一份合格的语义契约至少包含：

- 本次需求的实体与职责
- 状态与迁移
- 不变量
- 边界（输入输出、依赖方向）
- 验收条件

三个必要条件：

1. **可判定**：每条描述都能对应一个测试、指标或类型约束。
2. **可追溯**：契约条款能映射到本次交付的代码位置与证据。
3. **自包含**：只描述本次需求需要的东西，不承担定义长期概念的职责。

### 3.2 迭代闭环

```text
意图 → 立约 → 人审 → 代码交付 → 守约证据 → 验收 → 归档
```

- **人类和 AI 沟通确定语义契约**：人给意图与约束，AI 给出候选契约与歧义点，双方收敛。
- **AI 负责代码交付**：实现、测试、证据一并交付。
- **人类只审核和调整语义契约**：不读实现，只判断「这是不是我要的东西」。
- **归档**：交付后文档进入归档，不升级为法，也不作为下一个需求的模板。

### 3.3 人机分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 人 | 给意图、确认语义契约、调整语义、验收 | 读实现、逐行 review |
| AI | 契约提案、代码交付、生成证据、报告偏差 | 定义长期概念、修改立法 |
| 机器 | 跑规则、跑指标、拦截违约 | 判断「这样设计好不好」 |

### 3.4 一致性证据：审语义不等于审实现

只审语义有一个天然风险：契约没变，实现漂移。必须补三样：

| 证据 | 作用 |
|---|---|
| 契约测试 | 把契约中的不变量变成可执行测试 |
| 追溯矩阵 | 契约条款 → 代码位置 → 测试/指标 |
| 漂移告警 | 代码改了契约没改、或契约改了代码没改，自动报错 |

没有这三样，「审语义」就退化成「信任 AI」。

### 3.5 分级授权

| 层级 | 变更内容 | 归属 | 批准方 | 验收方式 |
|---|---|---|---|---|
| L0 | 实体内部实现，契约不变 | 功能区 | AI 自主 | 机器验收 |
| L1 | 实体内新增能力，契约不变 | 功能区 | AI 提交 | 自动证据 + 人抽查 |
| L2 | 修改契约或边界 | 立法流程 | 人批准 | 人工审概念变更 |
| L3 | 跨实体重构、依赖方向变更 | 立法流程 | 人主导 | 人工设计与验收 |

L0/L1 在迭代内完成；L2/L3 不属于需求迭代，转入独立的立法流程。

## 四、注意力经济学

新范式的核心资源不是算力，是**人的注意力**。

- 总注意力成本 = 立法成本（跨需求摊销）+ 迭代审核成本（每次立约）− 机器验证替代的部分。
- 立法贵而少，需求频而轻；两者分开计价，互不挤占。
- 并行度上限 = 边界清晰度，不是 AI 数量。两个 AI 要改同一个实体，说明分片错了，不是协调问题。
- 分片原则：一个分片 = 一个实体，或一个「契约不变的改动面」。同实体串行，跨实体并行；并行前先冻结接口。
- 衡量指标：人每次必须阅读的代码行数 / 概念数。这条线压不下去，10 个 AI 就是上限，100 个是幻觉。

## 五、反模式

**立法侧：**

- 用 `utils`、`common`、`helper`、`misc` 吸收无归属代码。
- 用大而模糊的概念掩盖不确定。
- 规则只写不执行。
- 指标只采集不设限。
- 把某个具体需求写进法条，导致法随需求漂移。
- 法条膨胀：把一次性约束当成长期法律。

**需求侧：**

- 把人肉 review 当质量门。
- 按文件或工作量分片并行。
- 语义契约写成脱离代码的文档，无法追溯。
- 把需求文档当成长期定义，交付后仍被后续需求引用。
- 在需求迭代里顺手改立法。
- 抽象后无法定位问题——那是含糊，不是抽象。

## 六、自检清单

### 立法自检

1. 这条法是否与具体需求无关？如果只对某个需求成立，它不该在这里。
2. 每条规则，有没有指标证明它仍然被执行？
3. 每个指标，能不能归因到唯一实体？
4. 稳定区是否足够小？里面每一条法是否都还在被使用？
5. 有没有「本应只有一份」的东西被复制成了多份？这是沙化的第一征兆。

### 需求自检

1. 本次语义契约是否可判定、可追溯、自包含？
2. 每个文件或模块，能不能用一句话说清「它是什么实体」（不含「工具 / 辅助 / 杂项」）？
3. 新需求是在「给已有实体加能力」，还是在「新建一个说不清归属的文件」？
4. 契约与代码是否有一致性证据，而不是靠人盯？
5. 一次改动，人需要阅读的代码行数能否压到「几个概念 + 几条证据」？

### 元原则

方法论自身也要满足这三条：每个实践都要有名字（语义）、有它保证的东西（规则）、有证明它有效的指标（度量）。做不到这三点的实践，只是仪式，迟早变成新的沙。

## 七、落地路线

两条线独立推进，不互为前置。

**立法线：**

1. **暗物质普查**：列出实体清单，标出无归属代码。
2. **单点闭环**：选 1~2 个高频实体，写契约 + 一条自动规则 + 一个指标，跑通「越界即阻断」。
3. **预算化**：把结构预算与注意力预算纳入 ratchet，逐圈扩大覆盖。
4. **定期退役**：清理零命中的法条，防止法条膨胀。

**需求线：**

1. **模板上线**：统一语义契约模板与验收条件格式。
2. **分级授权**：L0/L1 放行，L2/L3 转立法流程。
3. **一致性证据**：为高频需求补契约测试与追溯矩阵。
4. **归档机制**：需求文档交付即归档，不进入长期引用。

## 八、术语表

| 术语 | 含义 |
|---|---|
| 立法（稳定区） | 长期、跨需求的代码约束系统，目标是代码可控 |
| 需求迭代（功能区） | 单次需求的立约、代码交付与验收，交付即归档 |
| 语义立约 | 人机共同确定需求含义：实体、状态、不变量、边界、验收条件 |
| 语义契约 | 语义立约的产物，人与 AI 在本次需求中的唯一对接资料 |
| 代码交付 | 把语义契约翻译为代码结构并交付证据：数据结构、控制流、模块划分、错误处理，由 AI 承担 |
| 概念卡 | 立法侧一个实体的最小定义单元，含职责、契约、边界、owner、证据 |
| 注意力预算 | 人每次必须阅读的代码行数与概念数的比值上限 |
| Ratchet | 指标只允许变好、不允许回退的约束机制 |
| 暗物质 | 无归属、无名字、无契约的离散代码 |
| L0~L3 | 按「是否触碰契约与边界」划分的变更授权层级 |
