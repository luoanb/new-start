# Spec: Pulsar 应用平台（平台基建 · 应用模型 · 多执行环境）

> 状态：**探索 / 设计阶段**，架构分层与边界设计，不含落地实现细节。
> 原主题：Pulsar 插件系统。本版本将「插件」重新定位为应用包或兼容性形态，顶层抽象升级为「应用平台」。
> 关联：[后端架构重构 spec](./2026-09-06_13-55_pulsar-backend-architecture-redesign.md)、[Hook 三阶段分离 spec](./2026-09-12_10-42_hook-definition-registration-enablement.md)、[architecture.md](../pulsar/architecture.md)。

## Goal

Pulsar 需要从一个由宿主静态装配若干能力的应用，演进为一个可承载多类应用的应用平台。

本 spec 要回答四个问题：

1. **平台提供什么基建能力**：哪些能力是所有应用依赖的稳定平台能力，哪些只是平台提供的可选服务。
2. **应用是什么**：面向个人、面向 AI、以及一体双向的应用如何基于平台构建。
3. **如何执行应用**：平台侧采用编译型模型，应用侧采用解释型模型，并允许多个应用执行环境。
4. **现有能力如何迁移**：哪些保留在平台核心，哪些成为平台服务，哪些迁移为应用；迁移不改变既有核心运行语义。

本 spec 不再以“把所有现有能力整理成插件清单”为主要目标。旧的插件映射、贡献点清单和具体注册表改造方案全部删除，待平台边界确认后按独立 spec 重新设计。

## Done Contract

- 什么算完成：平台、平台服务、应用、应用执行环境四者的边界得到明确；应用模型和迁移原则获得用户确认。
- 由什么证明：本文档的架构分层、术语、边界表和 Open Questions 完成裁决。
- 哪些情况仍算未完成：仍有会改变平台核心边界或执行模型的关键问题未裁决；或具体实现方案被提前当作本 spec 的结论。

## Scope

### In

- 平台—应用—执行环境三层架构；
- 平台核心与平台服务的边界原则；
- 应用类型、应用包、应用实例与应用运行时；
- 编译型平台与解释型应用的关系；
- 多执行环境的抽象与约束；
- 现有能力的迁移分类原则和候选归位；
- 后续平台化工作的分期方向。

### Out

- 具体 Rust / TypeScript 文件结构、函数签名和最终数据格式；
- 具体注册表、命令分发、事件枚举改造方案；
- 应用市场、分发、签名和远程安装；
- 第三方原生动态库插件；
- 某一个具体应用的详细产品设计；
- 在本 spec 中直接修改代码。

## Restated Understanding

Pulsar 当前面对的不是单纯的“插件如何启停”问题，而是需要先建立一个类似小程序平台的基础架构：平台负责提供稳定的运行基础和受控能力，应用在平台上表达产品能力与 AI 能力。

平台和应用采用不同的技术模型：

- 平台侧是**编译型**的，负责固定协议、类型、权限、调度和基础设施；
- 应用侧是**解释型**的，平台读取应用描述、声明、脚本或工作流并执行；
- 应用可以由多个执行环境承载，但不能绕过平台定义的能力边界。

当前核心目标是先定清楚平台的边界，而不是继续扩展插件注册表设计。

## 一、核心立场

### 1. Pulsar 首先是应用平台，不是插件容器

平台是应用运行的宿主与基建。应用是平台上的产品能力单元；插件只是应用包、应用扩展或历史兼容称呼，不再是最高层架构抽象。

```text
Pulsar Platform
├── Platform Kernel
├── Platform Services
├── Platform SDK / Toolchain
└── Application Runtimes
    └── Applications
```

### 2. 平台定义边界，应用表达能力

平台负责定义：

- 应用可以访问哪些能力；
- 能力以什么协议被调用；
- 应用如何被加载、启动、暂停、恢复和停止；
- 应用如何声明权限、依赖和兼容的平台版本；
- 应用之间如何隔离以及如何通过平台服务协作。

应用负责表达：

- 面向谁提供能力；
- 使用哪些平台能力；
- 如何组织工具、工作流、AI 行为和 UI；
- 应用自身的状态、配置和交互逻辑。

应用不能自行定义新的内核注入位置，也不能绕过平台能力协议直接触碰平台内部状态。

### 3. 编译型平台与解释型应用分离

平台代码通过 Rust / TypeScript 等语言编译进宿主，形成稳定的运行基础。应用不要求以同一种语言编译进宿主，而是由应用执行环境解释和调度。

```text
Application Package
        │ manifest / declarations / scripts / workflows
        ▼
Application Runtime
        │ Platform Capability API
        ▼
Platform Services
        ▼
Platform Kernel
```

“解释型”不等于不受约束。应用仍需经过清单校验、能力授权、版本兼容性检查和运行时权限控制。

### 4. 平台核心不可替换，平台服务可演进，应用可拔插

- 平台核心承载 Pulsar 的运行不变量，不作为普通应用替换；
- 平台服务是平台向应用暴露的稳定能力，可按配置启用或由不同实现提供；
- 应用可以安装、启用、暂停、停用和更新；
- 应用执行环境是平台能力的一部分，不由单个应用自行决定安全边界。

## 二、术语

| 术语 | 含义 |
|---|---|
| **Platform（平台）** | 为多个应用提供统一运行基础、能力接口、生命周期和安全边界的系统。 |
| **Platform Kernel（平台核心）** | 不可由应用替换的运行骨架，承载轮次、会话、能力执行、权限、事件和运行时协调等不变量。 |
| **Platform Service（平台服务）** | 平台向应用提供的可复用能力，如工作区、模型、终端、持久化和任务调度。它受平台契约约束，但不必全部属于最小核心。 |
| **Platform SDK / Toolchain（平台 SDK / 工具链）** | 定义应用契约、清单、能力声明、类型检查、兼容性检查和应用包构建规则的编译期工具。 |
| **Application（应用）** | 基于平台能力构建的完整能力单元，拥有目标、入口、状态、交互和执行逻辑。 |
| **Application Package（应用包）** | 应用的清单、声明、解释内容、资源和可选脚本的组合。 |
| **Application Instance（应用实例）** | 应用在平台上的一次运行实例，拥有独立的配置、状态、权限上下文和生命周期。 |
| **Application Runtime（应用执行环境）** | 解释并执行应用包的环境，如声明式运行时、Lua 运行时、外部进程运行时或未来 WASM 运行时。 |
| **Capability（平台能力）** | 平台或平台服务对应用暴露的受控能力，应用只能通过能力协议访问。 |
| **Application Type（应用类型）** | 对应用交互方向的分类：面向个人、面向 AI、一体双向。 |
| **Plugin（插件）** | 兼容性术语。可以指编译进宿主的平台内置应用，也可以指可安装的应用包；不再作为顶层架构模型。 |

## 三、平台分层

### 3.1 平台核心

平台核心只保留所有应用必须依赖、且不能由应用改变的运行不变量：

- 会话与轮次协议；
- 能力调用与结果配对协议；
- 基础权限与安全边界；
- 应用生命周期协调；
- 基础事件与状态传播机制；
- 应用实例隔离；
- 平台版本与能力版本协商；
- 应用执行环境的装载与监管；
- 最小持久化、配置和任务协调抽象。

平台核心不应因为迁移某个领域能力而引入该领域的产品语义。

### 3.2 平台服务

平台服务是平台提供给应用的标准能力。它们可以有默认实现，也可以在不破坏平台契约的前提下替换实现。

候选平台服务包括：

- `WorkspaceService`：工作区、文件和路径能力；
- `ModelService`：模型与供应商调用；
- `TerminalService`：受控终端能力；
- `SearchService`：搜索与索引能力；
- `StorageService`：应用命名空间存储；
- `TaskService`：后台任务与取消；
- `EventService`：应用事件发布与订阅；
- `UIService`：应用视图、面板和消息块注册；
- `ConfigService`：应用配置声明和读取；
- `DocumentService`：手册、契约和应用资源访问。

“平台服务”不表示所有应用都默认启用。平台负责定义其能力契约、权限、生命周期和隔离方式；具体应用是否依赖，由应用清单声明。

### 3.3 平台 SDK / 工具链

平台 SDK 负责把编译期约束前移，至少包括：

- 应用清单和版本声明；
- 平台能力声明；
- 权限声明；
- 应用入口和应用类型声明；
- 应用包结构校验；
- 平台版本兼容性校验；
- 解释内容的静态检查；
- 应用资源和契约的打包。

SDK 不把应用编译成平台内核的一部分。它的作用是生成平台可加载、可校验、可解释的应用包。

## 四、应用模型

### 4.1 应用不是单个工具或视图

工具、Hook、View、Provider、Workflow 等是应用可以使用或声明的组成元素，不自动等同于应用本身。

一个应用应至少能够说明：

- 它服务的对象和目标；
- 它的入口和交互方式；
- 它依赖的平台能力；
- 它需要的权限；
- 它的运行状态与持久化范围；
- 它由哪个执行环境承载。

### 4.2 三类应用

#### 面向个人的应用

以人的交互、查看、编辑、配置和操作为主要入口。例如工作区管理、Git 管理、日志诊断等。

#### 面向 AI 的应用

以模型或 Agent 调用为主要入口，提供工具、上下文、策略、知识或工作流。例如搜索、模型接入、自动化任务等。

#### 一体双向应用

同时面向个人和 AI：人可以通过 UI 观察、配置和干预，AI 可以通过平台能力调用。对话、Topic、Poller 等能力可能属于这一类，但最终归属需按产品目标判断，而不能仅按当前代码目录判断。

### 4.3 应用包的概念形状

应用包的最终格式另立 spec，本阶段只定义语义：

```text
Application Package
├── identity
├── application_type
├── platform_compatibility
├── runtime_requirement
├── capabilities
├── permissions
├── entrypoints
├── declarations / workflows / scripts
├── ui resources
└── storage and configuration schema
```

应用包应能被不同执行环境识别。执行环境不应改变应用对平台能力的语义理解。

### 4.4 应用生命周期

应用生命周期至少包括：

```text
Discovered → Validated → Loaded → Running
                              │
                 ┌────────────┴────────────┐
                 ▼                         ▼
              Paused                    Stopped
```

约束：

- 应用实例启动前必须完成清单、版本、依赖和权限校验；
- 停止应用不默认删除其数据；
- 平台不得静默打断不变量仍未收敛的核心轮次；
- 应用执行环境必须能够取消或回收应用发起的后台任务；
- 应用之间通过平台服务或事件协作，不直接依赖彼此内部实现。

## 五、多执行环境

平台允许存在多个应用执行环境，但执行环境必须遵守统一的 Application Runtime Contract。

| 执行环境 | 适合内容 | 隔离方式 | 阶段 |
|---|---|---|---|
| `declarative` | 工具声明、命令模板、工作流、提示词和资源 | 平台解释与能力授权 | 首期优先 |
| `script` | 需要少量逻辑的工具、Hook 和工作流 | 脚本沙箱与权限 | 后续 |
| `external` | 独立服务、远程能力、复杂运行逻辑 | 进程 / IPC / HTTP 边界 | 后续 |
| `builtin` | 平台内置且高信任的默认应用 | 编译进宿主，但仍遵守应用契约 | 迁移过渡 |
| `wasm` | 需要更强隔离的可移植逻辑 | WASM 沙箱 | 未来评估 |

`builtin` 是迁移和性能需要下的实现形态，不代表应用可以绕过平台契约。长期目标是让应用模型与执行环境解耦：同一个应用在允许的情况下可以由不同执行环境承载。

执行环境必须提供：

- 应用加载与卸载；
- 应用入口调用；
- 平台能力代理；
- 权限检查；
- 日志、错误和取消；
- 资源与生命周期回收；
- 与平台版本的兼容性报告。

应用不得假定某个执行环境一定存在，除非在清单中声明运行时要求。

## 六、平台核心、平台服务与应用的边界判定

采用以下判定顺序，而不是按照当前目录或现有模块名称归类：

1. **是否是所有应用都必须遵守的运行不变量？**是，则进入平台核心。
2. **是否是多个应用复用、但可以独立演进或按需启用的能力？**是，则优先进入平台服务。
3. **是否带有明确的领域目标、产品交互、AI 行为或业务状态？**是，则优先建模为应用。
4. **是否只是某个应用的内部实现？**是，则留在应用内部，不暴露为平台能力。
5. **是否只能通过替换轮次、会话或能力执行骨架才能实现？**是，则不得作为普通应用能力开放。

初步分类如下：

| 现有能力 | 初步归位 | 说明 |
|---|---|---|
| 轮次、会话不变量、能力执行协议 | 平台核心 | 所有应用共同依赖，不能由应用替换 |
| 权限、事件基础设施、应用生命周期 | 平台核心 | 提供跨应用边界 |
| 工作区、存储、任务、配置 | 平台服务 | 通用能力，按权限和命名空间开放 |
| 模型与供应商接入 | 平台服务候选 | 需要区分调用协议与供应商产品管理 |
| 终端、搜索、文件操作 | 平台服务候选 | 作为受控能力暴露，不等于全部 UI 内置 |
| 对话 UI 与消息渲染 | 平台默认应用 / 一体双向应用候选 | 需区分宿主壳与产品能力 |
| Topic、Poller、Neuron | 应用候选 | 具有明确领域语义，不应仅因被核心调用就进入核心 |
| Git | 面向个人的应用候选 | 依赖工作区平台服务 |
| MCP、动态工具 | AI 应用或声明式应用候选 | 适合作为应用包 / 执行环境样例 |
| 日志、诊断、应用管理 | 平台管理应用候选 | 面向平台治理，但不必全部进入内核 |

该表是迁移起点，不是最终冻结的模块清单。

## 七、现有能力迁移原则

### 7.1 迁移目标

迁移的目标不是机械地把每个模块改名为应用，而是：

- 缩小平台核心；
- 把领域语义移出平台核心；
- 通过平台服务暴露稳定能力；
- 让应用拥有清晰的入口、状态、权限和生命周期；
- 让同一应用可以逐步从 `builtin` 迁移到解释型执行环境。

### 7.2 迁移顺序

1. 先确认平台核心不变量；
2. 定义平台服务契约和权限边界；
3. 选取一个最小应用验证应用包和执行环境；
4. 将现有领域能力按产品目标迁移为应用；
5. 最后处理应用间依赖、兼容性和替换实现。

### 7.3 迁移期间的兼容性

现有固定命令、事件、配置和 `.pulsar/` 数据布局可以通过兼容适配逐步迁移，但不能因为迁移而改变：

- 轮次协议；
- 会话不变量；
- 能力执行结果语义；
- 事实事件的可靠性；
- 既有安全边界；
- 已盖章文档规定的工具、终端、文件操作和供应商语义。

发现实现与既有 spec 不一致时，先进行文档反向同步，再决定迁移方案。

## 八、平台与应用之间的契约

### 8.1 平台向应用提供

平台向应用提供的是受控的 Capability API，而不是内部对象引用：

```text
ApplicationContext
├── capability(name, version)
├── storage(namespace)
├── config(namespace)
├── events(namespace)
├── ui(surface)
├── tasks(cancellation)
├── logger(scope)
└── runtime(metadata)
```

具体接口和类型不在本 spec 中确定。

### 8.2 应用向平台声明

应用至少声明：

- 应用身份和版本；
- 应用类型；
- 兼容的平台版本；
- 所需执行环境；
- 所需平台能力及版本；
- 权限；
- 入口和可选 UI 表面；
- 数据与配置命名空间；
- 与其他应用的依赖。

### 8.3 平台不向应用承诺内部结构

应用不能依赖以下内容：

- 平台内部模块路径；
- 某个具体注册表的实现；
- 某个宿主字段或组合根结构；
- 某个执行环境的私有 API；
- 未进入平台契约的内部事件。

## 九、后续分期方向

| 阶段 | 目标 | 主要产出 |
|---|---|---|
| P0 | 平台边界 | 平台核心、平台服务、应用的边界与最小契约 |
| P1 | 应用契约 | Application Manifest、应用包结构、SDK 约束 |
| P2 | 首个执行环境 | 声明式应用运行时，以及一个最小应用样例 |
| P3 | 内置能力迁移 | 将现有领域能力按迁移原则包装为内置应用 |
| P4 | 多执行环境 | 脚本、外部进程等运行时与统一生命周期 |
| P5 | 应用管理 | 应用实例管理、配置、权限、更新与诊断 |

具体每一期另立 spec，不在本文档直接进入实现计划。
