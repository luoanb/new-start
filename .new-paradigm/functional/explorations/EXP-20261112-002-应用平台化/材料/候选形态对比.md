# 平台形态候选对比

> 采集时间：2026-11-12
> 用途：支撑 `探索.md` 第二章三个候选的七维度回答与失败预演；本文件不参与裁决，不含人的决策。

## 共同前提（用户已定，三候选不再区分）

- 应用 = 内聚包，自带页面、服务、Skill、工具等贡献；跨应用复用只走上下文贡献。
- 桌面 = OS 式，不承载业务；窗口与后台是桌面提供的能力，应用调用；生命周期独立，后台受桌面管控。
- 身份 / 数据 / 授权的延续按 Android 约定；身份 = 应用 id + 签名。
- 依赖上游「插座边界」A′ 方向：应用对应插座树中一个开座者子树；上下文贡献即开座者划定的作用域。

三候选的唯一分歧轴：**应用代码在哪里运行、崩溃与权限由谁隔离**。

## 七维度对比

| 维度 | A 同进程子树 | B 每应用独立进程 | C 按信任分轨 |
|---|---|---|---|
| 应用身份 | 清单 id + 签名；签名由安装来源签发（内建=平台、人/AI=本机密钥、社区=发布者） | 同 A | 同 A，签名同时决定运行轨道 |
| 内容归属 | 贡献是应用根插件开出的子插座，与宿主同进程装载 | 贡献在应用进程内装载，经 IPC 投影到桌面 | 高信任轨同 A，低信任轨同 B |
| 运行边界 | 窗口 / 后台由桌面管；进程与崩溃无隔离，应用崩溃即宿主崩溃 | 窗口 / 后台由桌面管；进程与崩溃按应用隔离 | 高信任轨无隔离，低信任轨按应用隔离 |
| 数据延续 | 每应用独立数据目录，按 Android 规则 | 同 A | 同 A |
| 权限与账本 | 门卫在应用根插件边界拦截，同进程内只能审计不能强制 | 门卫在 IPC 边界拦截，可强制 | 两条拦截路径，账本需合并 |
| 来源与信任 | 来源只影响审查与授权 | 来源只影响审查与授权 | 来源决定轨道，升降轨需重新安装 |
| 增长方式 | 安装 = 落包 + 注册清单，宿主热装载，桌面即时感知 | 安装 = 落包 + 拉起进程，桌面经进程事件感知 | 两套安装路径按轨道分发 |

## 最强反对与六个月失败预演

### A 同进程子树

- 最强反对：同进程即拥有宿主全部权限，Android 式权限与崩溃隔离在技术上不可强制，只能靠门卫审计事后追责。
- 失败预演：AI 写的应用反复把整个桌面带崩，用户关掉 AI 安装通道，「它会自己长」落空。

### B 每应用独立进程

- 最强反对：上下文贡献中的依赖注入与页面渲染跨进程后退化为 RPC 与远程 DOM，插座四种消费机制全部要序列化，页面级组合（一个应用往另一个应用的槽填组件）几乎不可做。
- 失败预演：六个月全部投入在 IPC 与序列化层，没有一个真正的应用跑起来；或应用之间只能各开各窗，桌面退化为启动器。

### C 按信任分轨

- 最强反对：两条运行轨道就是两条门卫调用路径，与愿景「一个门卫、一本账」直接冲突，也和上游「插座边界」已识别的账本分裂风险同源。
- 失败预演：所有 AI 写的应用都因性能或依赖注入需求申请升到高信任轨，低信任轨空转，最终退化为 A 却多了一套复杂度。
