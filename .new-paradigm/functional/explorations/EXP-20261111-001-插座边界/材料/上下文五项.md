# 上下文五项（开座契约草案）

> 采集时间：2026-11-12
> 用途：回答原开放问题“开座机制的最小契约是什么”。本文件是草案，不参与裁决；人确认后由需求立约另行固化。

## 1. 结论

“同层共享上下文”不是实体，是**开座者划定的作用域**。插在同一插座上的插件，在该作用域内共享五种机制；不存在一个叫 `SharedContext` 的对象。

## 2. 五项（按信息流动方向枚举）

| 方向 | 项 | 含义 | 现状 |
|---|---|---|---|
| 向上拉 | 依赖注入 | 插件声明“我要一个能做 X 的能力”，按能力名注入 | Cordis `inject` 已有 |
| 向外推 | 事件广播 | 插件告诉同层发生了什么，无人听则无事发生 | `StateChange` 雏形 |
| 向下流 | 开座者赋予 | 插座主人交给子插件的东西：配置、父作用域、日志前缀 | `RuntimeContext` 雏形 |
| 一直在 | 共享状态 | 同层都能读、按授权能写的数据 | **无归宿** |
| 收回来 | 生命周期 | 插件登记“我留下了什么”，开座者决定“何时清”，内核保证子先父后、逆序 | `ctx.effect` 已有登记；PENDING 插件清理项未挂 fiber，路由残留 |

判断“还有没有第六项”的方法：新候选若能归入以上某一方向，即为变体而非新项。已知变体：配置 → 向下流；RPC → 依赖注入的传输形式；状态订阅 → 共享状态 + 事件广播。

## 3. 开座契约骨架（由五项推出）

开座者插件要开出新插座，至少向内核声明：

- 插座名与该插座的契约形态（服务接口 / 槽名 / 提示词 / JSON Schema 之一）
- 向下赋予什么（五项中的第 3 项的内容）
- 子插件的生命周期归谁清理（第 5 项的归属）

内核回给开座者：

- 该插座的作用域标识，供门卫按作用域记账
- 事件广播与依赖注入在该作用域内的通道

## 4. 两条纪律

- 注入名必须是能力名，禁止是插件 id。违反即耦合到插件而非契约。
- 跨插件调用过门卫。A 调 B 的服务与 AI 调工具同一本账。

## 5. 待人决定

共享状态的归宿：

- 选项甲：做成开座者注入的 `state` 服务，读写走注入路径，门卫按 key 授权；响应式靠事件广播补。
- 选项乙：独立 Store + 订阅，响应式原生；代价是门卫要认第二种调用路径。
