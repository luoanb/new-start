# 产品定义规则

> 文档状态：生效
> 确认记录：2026-11-14 用户确认三份正文结构的产品定义规则生效。
> 上位依据：《编程新范式》《落地策略》《术语表》《文档治理规则》《治理规则编写规则》《目录结构规范》《需求探索规则》《需求契约追溯规则》
> 适用范围：`functional/product/` 下的产品边界、产品形态、能力构成三份正文，及其对需求、代码契约和实现的约束关系
> 下位产物：产品定义实例、需求实例、代码契约、实现代码、产品定义模板

## 一、目的

在愿景与需求之间建立一层参与裁决的产品级语义，使产品整体边界、产品形态、能力划分、跨需求规则和冲突裁决有唯一依据，避免每次需求重新定义产品。本文件使用 `PDEF` 作为产品定义领域的规则编号前缀。

本规则中，“产品定义”指愿景与需求之间的整个语义层，由三份正文组成；不指任何单一文件。

## 二、规则

### PDEF-001 组成与唯一权威

- **规则**：产品定义必须由 `functional/product/` 下的三份正文组成：`产品边界.md`、`产品形态.md`、`能力构成.md`。每类产品级语义只允许出现在其中一份文件中，文件之间必须引用而禁止复制。产品定义参与裁决；探索文档、生成式契约总览和需求文档禁止替代、复制或改写其语义。同一产品禁止存在第四份承载产品级语义的正文。
- **理由**：愿景只提供方向，需求只覆盖单次变化，二者之间缺少可裁决的产品整体语义；按语义拆分文件可以让变化频率不同的内容分别确认，同时保持每类语义仍只有一个来源。
- **验证**：检查三份文件的路径；AI 审查是否有同一语义出现在多个文件，以及需求、契约是否引用而非复制产品定义。
- **例外**：主干流程正文按 PDEF-016 拆出的文件不视为第四份正文。

### PDEF-002 上位依据与状态

- **规则**：产品定义的上位依据必须是生效愿景。愿景未生效时，三份正文只能处于 `草案` 或 `待确认`，不参与裁决。三份正文各自声明状态、各自确认；一份生效不代表其余生效。愿景发生实质性变更后，必须重新确认受影响正文与愿景一致；未确认前，受影响条目不得用于裁决。
- **理由**：产品定义是愿景的具体化，不能反向改变愿景的方向和边界；分文件确认使形态和能力可以先后定稿。
- **验证**：人工确认愿景状态与各文件状态；AI 审查元数据和变更说明。
- **例外**：无。

### PDEF-003 必备语义与归属

- **规则**：产品定义必须包含六类语义，归属如下：
  - `产品边界.md`：产品定位、跨需求不变量、产品级非目标、冲突裁决原则；产品级质量属性按需包含。
  - `产品形态.md`：产品形态。
  - `能力构成.md`：能力构成与职责边界。
  某类语义缺少内容时必须写明“无”及判断依据，禁止省略对应章节，也禁止把它写到其他文件。
- **理由**：六类语义分别回答产品是什么、长什么样、由什么组成、什么永远成立、什么永不做、冲突听谁的；固定归属使读者能从文件名直接定位。
- **验证**：AI 或人工逐项检查六类语义是否存在、非空且位于指定文件。
- **例外**：无。

### PDEF-004 产品定位

- **规则**：产品定位必须用一句话说明产品为谁提供什么，并说明与最易混淆的相邻产品的区别。产品定位禁止写功能清单、实现方案或迭代计划。
- **理由**：定位是判断一个陌生诉求是否属于本产品的第一道边界。
- **验证**：人工判断；给出一个陌生诉求，检查仅凭本节能否判定归属。
- **例外**：无。

### PDEF-005 能力构成与职责边界

- **规则**：`能力构成.md` 必须列出产品级能力，每项能力必须写明“负责”“不负责”和“使用者入口”。入口必须是 `产品形态.md` 中已声明的入口，禁止在能力表中新增入口。能力必须按可独立验证的职责划分，禁止按代码模块、目录结构或技术分层划分。可以引用代码契约路径，但生成式契约总览不得作为能力划分依据。
- **理由**：职责边界是判断需求是否越界、能力是否重复的依据；入口字段把能力与形态对应起来，防止两份文件各说各话。
- **验证**：AI 审查每项能力的“不负责”是否非空、入口是否能在产品形态中定位；人工判断划分粒度是否稳定。
- **例外**：尚无使用者直接触达的内部能力，入口可以写“无直接入口”并说明由哪项能力间接触达。

### PDEF-006 跨需求不变量

- **规则**：跨需求不变量必须使用 `必须` 或 `禁止` 表达，每条必须存在可被某份需求违反并因此判定违规的情形。禁止使用 `尽量`、`优先` 等无法判定违规的表达。
- **理由**：不能被人或需求违反的规则，无法用于裁决。
- **验证**：为每条不变量构造一个违反案例；构造不出时视为不合格。
- **例外**：无。

### PDEF-007 产品级非目标

- **规则**：产品级非目标必须写明长期不做的方向及其理由或替代方案。产品级非目标不随迭代自动解除；解除必须修改产品边界并重新确认。单次需求的“非目标”禁止写入本节。
- **理由**：防止范围在多次迭代中逐次累积漂移。
- **验证**：AI 审查每条非目标是否含理由；人工确认其是否仍长期有效。
- **例外**：无。

### PDEF-008 冲突裁决原则

- **规则**：冲突裁决原则必须以有序列表给出，顺序即优先级。每条原则必须能对具体冲突给出唯一结论，禁止并列无序或同时成立。
- **理由**：两份需求或两个能力职责冲突时，需要唯一且可预期的排序。
- **验证**：用真实或构造的冲突场景检验；无法得出唯一结论时视为不合格。
- **例外**：无。

### PDEF-009 表达边界

- **规则**：产品定义禁止写入实现方案、数据字段、页面布局、控件、视觉样式、文件路径清单和迭代安排。业务概念必须使用产品术语表中已生效的规范名称；术语表未定义时，必须先补充并确认术语表，再写入产品定义。产品定义禁止重复定义术语。
- **理由**：产品语义、实现语义、表现层语义和名词定义必须分层，避免出现第二份权威正文。
- **验证**：AI 审查实现细节、页面细节与就地定义；人工判断术语引用是否正确。
- **例外**：影响产品边界的技术约束，以及 PDEF-014 规定的形态语义，必须写入；写入时必须说明其产品影响。

### PDEF-010 篇幅与结构

- **规则**：产品定义不设行数上限，篇幅由判断项数量决定。每份正文必须按 PDEF-003 分配给它的语义分章，每条结论先行、一条一个判断。禁止为凑结构创建空章节，也禁止把不同语义合并到同一章节。单份正文超出 Agent 工作指引的审阅篇幅约束时，只能按 PDEF-016 拆出主干流程正文，禁止新建其他文件类型。
- **理由**：行数是排版度量，不是语义完备度量；篇幅压力应通过已定义的拆分方式释放，而不是创造新的权威文件。
- **验证**：AI 审查章节与语义的对应关系及文件数量；人工判断条目是否空泛或不可裁决。
- **例外**：无。

### PDEF-011 确认与变更

- **规则**：任一正文从 `草案` 或 `待确认` 变为 `生效`，必须获得用户明确批准。变更时必须说明修改原因、影响范围和受影响的需求、契约与其他产品定义正文。新增、删除或修改形态条目、能力、不变量、非目标和裁决原则属于实质性变更，必须重新确认，AI 禁止单方面完成。历史版本由 Git 保存，禁止按需求复制完整副本。
- **理由**：产品语义会沿需求与契约向下传播，也会在三份正文之间传播，变更必须受控。
- **验证**：检查确认记录、变更说明及受影响下位产物与关联正文的同步结果。
- **例外**：错别字、排版和失效引用修复不要求重新确认，但必须保持可追溯。

### PDEF-012 追溯与反向同步

- **规则**：需求文档必须以“文件名 + 条目”声明其依据的产品定义条目，并说明本次是否改变产品语义。需要改变时，必须先修改对应正文并完成确认，再确认需求。产品定义与需求冲突时，以产品定义为准；代码契约和实现禁止反向约束产品定义。
- **理由**：产品定义是需求的共同上位；只有单向依赖，才能发现两份需求之间的冲突。
- **验证**：抽查需求能否定位到具体文件与条目；AI 审查是否存在未修改产品定义却改变产品语义的需求。
- **例外**：无。

### PDEF-013 配套模板

- **规则**：起草或更新任一正文时，应该以 [`产品定义模板`](../templates/产品定义模板.md) 中对应骨架作为默认结构。模板只提供推荐格式，禁止覆盖或修改本规则语义；发生冲突时以本规则为准。
- **理由**：规则定义必须满足的语义，模板降低重复编排成本。
- **验证**：检查模板与规则语义是否一致，以及模板是否被当作独立权威来源。
- **例外**：使用其他结构时，仍必须覆盖 PDEF-003 分配给该文件的全部必备语义。

### PDEF-014 产品形态

- **规则**：`产品形态.md` 必须回答四项：载体形态（产品以什么形式存在并被运行）、使用者与入口（哪类使用者从哪里进入产品）、核心对象（使用者在产品中操作的主要对象及其关系）、主干流程（使用者达成愿景所述结果的主要路径，一流程一条）。四项只写到使用者能辨认产品的粒度，禁止写页面结构、交互状态和视觉约束。
- **理由**：没有形态，第一份需求就必须自行推断产品是什么，而这正是最该由人先定的事；形态决定后续需求能否越界，因此必须可裁决。
- **验证**：人工判断，给出一个陌生需求，检查仅凭本文件能否判定它是否改变了产品形态；AI 审查是否混入页面级细节。
- **例外**：无。

### PDEF-015 正文间优先级

- **规则**：三份正文之间发生冲突时，必须按 `产品边界.md` > `产品形态.md` > `能力构成.md` 的顺序裁决；低优先级正文与高优先级正文冲突的条目不得用于裁决，必须修改后重新确认。
- **理由**：拆分后的文件各自确认，可能在不同时间出现不一致；需要固定顺序才能得到唯一结论。
- **验证**：AI 审查三份正文的交叉引用是否一致；发现冲突时检查是否按顺序处理。
- **例外**：无。

### PDEF-016 主干流程拆分

- **规则**：主干流程正文可以从 `产品形态.md` 拆到 `functional/product/flows/<流程名>.md`。拆分后 `产品形态.md` 必须保留每条流程的一句话索引及链接，流程文件必须声明其上位依据为 `产品形态.md`，并与 `产品形态.md` 同状态、同批确认。这是产品定义唯一允许的第二级拆分；`产品边界.md` 和 `能力构成.md` 禁止再拆。
- **理由**：主干流程是形态中最可能超长的部分，拆出后不改变语义归属；限制其他文件拆分可以防止产品定义碎片化。
- **验证**：检查索引与流程文件是否一一对应、状态是否一致；AI 审查是否出现其他拆分文件。
- **例外**：无。

## 三、统一例外要求

规则条目的例外字段是唯一允许声明例外的位置。任何例外不得使产品定义与生效愿景冲突，也不得由 AI 单方面新增或删除产品语义。
