# 代码契约规则

> 文档状态：生效
> 上位依据：《编程新范式》《落地策略》《术语表》《文档治理规则》《治理规则编写规则》《目录结构规范》《需求契约追溯规则》
> 适用范围：`functional/contracts/` 下的当前有效代码契约
> 下位产物：代码契约、实现代码、测试及契约一致性检查能力

## 一、目的

规定代码契约的划分粒度、外部行为表达和版本维护方式，使一个契约能够简洁描述一个内聚能力的完整操作面，并作为实现与验证的直接依据。本文件使用 `CTR` 作为代码契约领域的规则编号前缀。

## 二、规则

### CTR-001 契约划分粒度

- **规则**：一个代码契约必须对应一个内聚能力或服务边界，并可以包含该边界内的多项相关对外操作。禁止按单个函数机械拆分契约，也禁止将缺少共同职责的整个业务领域合并为一个大型契约。
- **理由**：能力级粒度既能集中表达共享语义，又能避免契约碎片化或无限膨胀。
- **验证**：人工或 AI 检查契约内操作是否共享明确职责，以及拆分或合并后边界是否更清晰。
- **例外**：只有一个对外操作的能力仍可以单独形成契约，但划分依据必须是稳定职责而非函数数量。

### CTR-002 存放与标识

- **规则**：代码契约必须存放于 `functional/contracts/<domain>/<capability-name>.md`。`domain` 和 `capability-name` 必须采用英文小写 `kebab-case`，并与实现中的稳定领域、包、模块或公开能力命名对应；文档标题可以补充中文解释。契约标识必须采用 `CTR-<领域代号>-NNN`。同一标识和逻辑能力只能存在一份当前有效正文。
- **理由**：与代码能力对应的稳定英文路径可以减少文档名与实现名之间的转换成本，并使当前契约无需遍历历史需求即可定位。
- **验证**：检查路径、英文命名、与实现能力的对应关系、契约标识唯一性和重复正文。
- **例外**：尚无实现的新能力使用计划中的英文代码命名；首次实现若改变该命名，必须先同步重命名契约及需求侧引用。领域尚未形成通用代号时，必须先在该领域首份契约中声明代号含义。

### CTR-003 职责边界

- **规则**：代码契约必须用简短说明明确该能力负责什么和不负责什么。契约中的全部操作、类型、错误和保证必须属于该职责边界。
- **理由**：职责边界是判断操作是否内聚、契约是否需要拆分的依据。
- **验证**：人工判断每项契约内容是否能由同一职责解释；AI 审查越界或重复能力。
- **例外**：无。

### CTR-004 操作签名

- **规则**：对外操作必须优先使用接近函数签名的紧凑形式表达，例如 `operation(input) -> output`，并在必要时补充输入条件、输出语义或操作级错误。签名只表达外部可观察能力，不要求对应某个具体编程语言函数。
- **理由**：签名能够低成本表达操作面，同时保持语言、框架和传输协议无关。
- **验证**：AI 审查每项操作是否具有明确名称、输入和结果，人工确认其是否准确表达预期能力。
- **例外**：事件、消息或持续数据流可以使用等价的发布、订阅或流式表达，不强制伪装为同步函数。

### CTR-005 公共类型与错误

- **规则**：被多项操作共享的输入、输出类型和稳定错误标识必须在契约级统一定义，禁止在各操作下重复产生含义不同的副本。只被单项操作使用且语义简单的类型可以内联表达。
- **理由**：共享定义可以缩短契约，并防止同一概念在不同操作中漂移。
- **验证**：检查重复类型、同名异义字段和不稳定的自然语言错误判断。
- **例外**：无。

### CTR-006 整体保证

- **规则**：代码契约必须列出跨操作持续成立的整体保证或关键不变量。每项保证必须可以通过外部结果、状态变化或可获得证据进行判断。
- **理由**：操作签名描述“能做什么”，整体保证描述“无论如何都必须成立什么”。
- **验证**：人工或 AI 检查保证是否明确、可观察，并能约束实现或测试。
- **例外**：确认不存在跨操作保证时，可以明确记录“无”，但不得省略判断。

### CTR-007 按需扩展

- **规则**：状态转换、兼容性和操作级详细场景只在能力实际需要时补充，禁止为满足固定模板创建空章节。具体章节名称和顺序不构成强制约束。
- **理由**：按需扩展使简单契约保持简洁，同时允许复杂能力表达必要语义。
- **验证**：检查扩展内容是否服务于实际行为约束，以及是否存在无信息空章节。
- **例外**：无。

### CTR-008 实现隔离

- **规则**：代码契约禁止规定不影响外部行为的内部类结构、数据库选型、算法细节或框架用法。会影响兼容性、性能承诺、安全边界或可观察结果的技术约束必须表达。
- **理由**：契约应稳定约束结果，同时允许内部实现被替换。
- **验证**：AI 审查实现细节是否具有外部必要性，人工判断技术约束是否影响用户或调用方。
- **例外**：法律、合规或运行环境明确要求的实现限制可以纳入契约，但必须说明其外部约束来源。

### CTR-009 当前版本与历史

- **规则**：契约变更必须原位更新当前有效正文，历史版本由 Git 保存，禁止按需求复制完整契约。契约正文禁止维护关联需求列表；变更来源通过需求侧引用和 Git 历史查询。
- **理由**：项目需要一个可直接定位的当前契约，而不是多份按迭代分散的版本。
- **验证**：检查同一能力是否存在多个当前副本，以及契约中是否累积需求清单。
- **例外**：不兼容版本需要长期并行维护时，可以建立明确版本边界的独立契约，但必须说明并行范围和退出条件。

### CTR-010 可验证性

- **规则**：契约中的操作、错误和整体保证必须使用无歧义语言，并达到可以据此设计测试或检查的程度。尚不能验证的关键语义必须作为待决策项处理，禁止推定实现已经满足。
- **理由**：代码契约只有能够约束实现并支持验证时才具有交付价值。
- **验证**：尝试为每项关键语义给出至少一种可观察验证方式；无法给出时视为未完成。
- **例外**：需要人工判断的质量属性可以使用人工验收，但必须声明判断依据。

### CTR-011 配套模板

- **规则**：创建或更新代码契约时，应该以 [`代码契约模板`](../templates/代码契约模板.md) 作为默认表达骨架，并按 CTR-007 删除、调整或补充实际需要的章节。模板只提供推荐格式，禁止覆盖或修改本规则语义；发生冲突时必须以本规则为准。
- **理由**：规则负责定义必须满足的语义，模板负责降低重复编排成本，二者分工可以兼顾一致性与简洁性。
- **验证**：检查契约是否覆盖本规则要求的适用语义，并确认模板未被当作独立权威来源。
- **例外**：使用其他表达结构时，必须仍能清晰覆盖职责边界、操作签名、公共类型、错误、整体保证和适用的扩展语义。

## 三、统一例外要求

本规则不强制固定章节模板，但任何表达形式都必须覆盖适用的职责边界、操作签名、公共类型、错误、整体保证和按需扩展语义。

## 四、变更说明

- 首版：建立能力级契约粒度、多操作签名、共享定义、整体保证、实现隔离和当前版本维护规则。
- 本次：引入代码契约参考模板，明确规则与模板的权威边界和默认使用方式。
- 本次：契约目录和文件名统一采用与代码能力对应的英文小写 `kebab-case`。
