# 代码契约规则

> 文档状态：生效
> 上位依据：《编程新范式》《落地策略》《术语表》《文档治理规则》《治理规则编写规则》《目录结构规范》《需求契约追溯规则》
> 适用范围：`functional/contracts/` 下的当前有效代码契约
> 下位产物：能力契约、协作契约、契约总览、实现代码、测试及契约一致性检查能力

## 一、目的

规定能力契约、协作契约及其关系总览的职责边界、外部行为表达和版本维护方式，使单个能力与跨能力协作都能成为实现与验证的直接依据。本文件使用 `CTR` 作为代码契约领域的规则编号前缀。

## 二、规则

### CTR-001 契约类型与划分粒度

- **规则**：代码契约分为能力契约和协作契约。能力契约必须对应一个内聚能力或服务边界，并可以包含该边界内的多项相关对外操作；协作契约必须对应两个或多个能力之间一组具有共同目标的稳定协作。禁止按单个函数机械拆分能力契约，也禁止把整个业务领域或所有关系合并为一个大型契约。
- **理由**：能力契约描述稳定节点，协作契约描述跨节点行为；分开表达可以避免关系语义被重复写入多个能力契约。
- **验证**：人工或 AI 检查能力契约内操作是否共享职责，协作契约内关系是否服务于同一协作目标，以及拆分或合并后边界是否更清晰。
- **例外**：只有一个对外操作的能力仍可以形成能力契约；只有一条跨能力关系的协作仍可以形成协作契约，但划分依据必须是稳定职责或协作目标。

### CTR-002 存放与标识

- **规则**：能力契约必须存放于 `functional/contracts/<domain>/<capability-name>.md`，协作契约必须存放于 `functional/contracts/<domain>/<collaboration-name>-collaboration.md`。路径名称必须采用英文小写 `kebab-case`，并与稳定领域、代码能力或协作目标对应；文档标题可以补充中文解释。契约标识必须采用 `CTR-<领域代号>-NNN`。同一标识、逻辑能力或协作目标只能存在一份当前有效正文。
- **理由**：与代码能力对应的稳定英文路径可以减少文档名与实现名之间的转换成本，并使当前契约无需遍历历史需求即可定位。
- **验证**：检查路径、英文命名、与实现能力或协作目标的对应关系、契约标识唯一性和重复正文。
- **例外**：尚无实现的新能力使用计划中的英文代码命名；首次实现若改变该命名，必须先同步重命名契约及需求侧引用。领域尚未形成通用代号时，必须先在该领域首份契约中声明代号含义。

### CTR-003 职责边界

- **规则**：能力契约必须明确该能力负责什么和不负责什么；协作契约必须明确参与能力、共同目标以及不属于本协作的相邻流程。契约中的全部操作、关系、错误和保证必须属于对应边界。
- **理由**：职责边界是判断操作是否内聚、契约是否需要拆分的依据。
- **验证**：人工判断每项契约内容是否能由同一职责解释；AI 审查越界或重复能力。
- **例外**：无。

### CTR-004 操作签名

- **规则**：能力契约的对外操作必须优先使用接近函数签名的紧凑形式表达，例如 `operation(input) -> output`，并在必要时补充输入条件、输出语义或操作级错误。签名只表达外部可观察能力，不要求对应某个具体编程语言函数。
- **理由**：签名能够低成本表达操作面，同时保持语言、框架和传输协议无关。
- **验证**：AI 审查每项操作是否具有明确名称、输入和结果，人工确认其是否准确表达预期能力。
- **例外**：事件、消息或持续数据流可以使用等价的发布、订阅或流式表达，不强制伪装为同步函数。

### CTR-005 公共类型与错误

- **规则**：被多项操作共享的输入、输出类型和稳定错误标识必须在契约级统一定义，禁止在各操作下重复产生含义不同的副本。只被单项操作使用且语义简单的类型可以内联表达。公共类型对应产品术语表中的业务概念时，必须使用该概念的规范名称或其对应的英文命名，只描述该概念在代码中的形状，禁止复制或改写产品术语表中的业务定义。
- **理由**：共享定义可以缩短契约，并防止同一概念在不同操作中漂移；业务含义由产品术语表唯一定义，契约只负责代码形状。
- **验证**：检查重复类型、同名异义字段和不稳定的自然语言错误判断；检查公共类型命名是否能映射到产品术语表，正文是否出现第二份业务定义。
- **例外**：无。

### CTR-006 整体保证

- **规则**：能力契约必须列出跨操作持续成立的整体保证，协作契约必须列出跨参与能力持续成立的协作保证。每项保证必须可以通过外部结果、状态变化或可获得证据进行判断。
- **理由**：操作签名描述“能做什么”，整体保证描述“无论如何都必须成立什么”。
- **验证**：人工或 AI 检查保证是否明确、可观察，并能约束实现或测试。
- **例外**：确认不存在跨操作保证时，可以明确记录“无”，但不得省略判断。

### CTR-007 按需扩展

- **规则**：状态转换、兼容性、能力内关系和操作级详细场景只在能力实际需要时补充；交互顺序、失败传播、补偿和一致性边界只在协作实际需要时补充。禁止为满足固定模板创建空章节。
- **理由**：按需扩展使简单契约保持简洁，同时允许复杂能力表达必要语义。
- **验证**：检查扩展内容是否服务于实际行为约束，以及是否存在无信息空章节。
- **例外**：无。

### CTR-008 实现隔离

- **规则**：代码契约禁止规定不影响外部行为的内部类结构、数据库选型、算法细节或框架用法。会影响兼容性、性能承诺、安全边界或可观察结果的技术约束必须表达。
- **理由**：契约应稳定约束结果，同时允许内部实现被替换。
- **验证**：AI 审查实现细节是否具有外部必要性，人工判断技术约束是否影响用户或调用方。
- **例外**：法律、合规或运行环境明确要求的实现限制可以纳入契约，但必须说明其外部约束来源。

### CTR-009 当前版本与历史

- **规则**：能力契约和协作契约变更必须原位更新当前有效正文，历史版本由 Git 保存，禁止按需求复制完整契约。契约正文禁止维护关联需求列表；变更来源通过需求侧引用和 Git 历史查询。
- **理由**：项目需要一个可直接定位的当前契约，而不是多份按迭代分散的版本。
- **验证**：检查同一能力是否存在多个当前副本，以及契约中是否累积需求清单。
- **例外**：不兼容版本需要长期并行维护时，可以建立明确版本边界的独立契约，但必须说明并行范围和退出条件。

### CTR-010 可验证性

- **规则**：契约中的操作、关系、依赖、错误和整体保证必须使用无歧义语言，并达到可以据此设计测试或检查的程度。尚不能验证的关键语义必须作为待决策项处理，禁止推定实现已经满足。
- **理由**：代码契约只有能够约束实现并支持验证时才具有交付价值。
- **验证**：尝试为每项关键语义给出至少一种可观察验证方式；无法给出时视为未完成。
- **例外**：需要人工判断的质量属性可以使用人工验收，但必须声明判断依据。

### CTR-011 配套模板

- **规则**：创建或更新能力契约时，应该以 [`代码契约模板`](../templates/代码契约模板.md) 作为默认骨架；创建或更新协作契约时，应该以 [`协作契约模板`](../templates/协作契约模板.md) 作为默认骨架。模板只提供推荐格式，禁止覆盖或修改本规则语义；发生冲突时必须以本规则为准。
- **理由**：规则负责定义必须满足的语义，模板负责降低重复编排成本，二者分工可以兼顾一致性与简洁性。
- **验证**：检查契约类型与模板是否对应、适用语义是否完整，并确认模板未被当作独立权威来源。
- **例外**：使用其他表达结构时，能力契约仍须覆盖职责边界、操作、类型、错误和保证；协作契约仍须覆盖参与能力、关系、依赖、失败处理和协作保证。

### CTR-012 能力内关系

- **规则**：同一能力边界内，只有会影响外部行为、生命周期、完整性或验收的实体关系才写入能力契约，并按适用情况说明关系两端、方向、基数、所有者、生命周期和完整性保证。普通内部类引用、可替换的数据结构和调用细节禁止进入契约。
- **理由**：能力内的重要关系需要约束实现，但内部结构不应被契约固化。
- **验证**：检查每条关系是否具有外部可观察影响，以及是否足以判断所有权、生命周期和完整性。
- **例外**：关系不存在或不影响外部语义时可以省略关系章节。

### CTR-013 跨能力协作

- **规则**：两个或多个能力之间的关系会影响调用方向、事件或数据流、状态一致性、失败传播、补偿或验收时，必须建立协作契约。协作契约必须声明参与能力及可定位路径，并以结构化关系声明记录关系起点、终点、类型、必需性和交互点；同一跨能力关系禁止在参与方能力契约中重复定义。
- **理由**：跨能力关系需要单一权威正文，才能避免双向维护和关系语义漂移。
- **验证**：检查参与契约是否存在、关系声明是否可唯一解析、正文是否解释关键交互与保证，以及其他契约是否复制同一关系。
- **例外**：仅被调用方自身就能完整定义、且不产生跨能力保证的普通调用，不要求单独建立协作契约。

### CTR-014 生成式契约总览

- **规则**：`functional/contracts/overview.md` 必须由当前生效的能力契约和协作契约生成，用于展示领域、能力、协作和依赖关系。总览必须声明“生成、禁止手工修改、不参与裁决”；总览与契约冲突或过期时，以契约正文为准并重新生成总览。
- **理由**：总览可以降低理解全局关系的成本，但不能成为第二份关系权威来源。
- **验证**：对照生效契约检查总览来源、链接和依赖图，并检查手工修改或过期状态。
- **例外**：项目尚无生效代码契约时可以不生成总览。

## 三、统一例外要求

本规则不强制固定章节顺序，但能力契约和协作契约必须分别覆盖其适用语义。生成式总览不得替代、覆盖或反向修改代码契约。
