## 一、落地目标

落地工作的目标不是只形成一组理念，而是交付一套用户能够按照操作手册执行的人机协同编程机制。用户将该机制接入具体项目后，应能依次完成项目初始化、语义立约、代码交付和质量检测。

最终结果至少应回答以下问题：

- 人和 AI 在每个阶段分别提供什么、完成什么；
- 项目中需要存放哪些文档、规则和工具；
- 一次需求如何从自然语言变成代码契约；
- AI 如何依据契约交付代码；
- 如何检测代码是否符合规则、契约和质量指标；
- 出现偏差时，应该回到哪一层修正。

## 二、设计原则

### 1. 机制与具体仓库解耦

可移植机制本身不依赖某一个业务仓库。它应以可复用的模板、协议、规则和工具存在，能够安装或接入不同项目。

接入项目后，机制会在工作区中生成或维护治理规则、Skill、文档模板、配置和脚本。这些项目内文件是机制的实例，不等同于机制本体。

因此，“脱离仓库”约束的是机制的可复用来源，“以普通项目文件落地”描述的是机制进入具体项目后的存在形态，二者并不冲突。

### 2. 用户可以照章操作

机制必须附带操作手册，而不能依赖设计者口头解释。操作手册应按真实任务组织，明确每一步的输入、动作、产物、责任主体和完成条件。

用户应能依据手册完成一次端到端协作，而不是只理解若干抽象原则。

### 3. 兼容主流 IDE 与 Agent

治理规则和功能区文档应优先采用普通文本文件和稳定的目录约定，使不同 IDE 与 Agent 都能读取。工具专用配置只能作为适配层，不应成为语义的唯一载体。

跨工具兼容性的核心不是假定存在一个统一的 Agent 协议，而是：

- 核心语义保持工具无关；
- 文件格式易于人和 AI 读取；
- 对特定 IDE 的能力通过独立适配器接入；
- 缺少某个适配器时，核心文档仍然有效。

“是否采用通用 Agent 协议”需要经过工具生态调研后单独决策，当前不把它视为已成立的前提。

### 4. 功能产物保持普通、可读

需求迭代文档和代码契约属于项目的常规文档，应与代码一同版本化，并能被人直接阅读和审核。

不能只把关键语义保存在聊天记录、某个模型的临时记忆或特定 IDE 的私有状态中，否则项目将无法稳定传承。

## 三、机制分层

完整机制分为四层：

### 1. 核心规范层

定义跨项目稳定的概念、阶段、角色、产物和基本原则，包括术语表、治理规则编写规范、语义立约规范以及代码交付规范。

### 2. 项目实例层

把核心规范映射为具体项目中的治理区和功能区。该层包含治理规则、Skill、指标配置、需求迭代文档和代码契约。

### 3. 工具执行层

提供指标采集、规则检查、契约一致性检查和交付编排能力。该层可以包含命令行工具、自动化脚本或 CI 集成。

### 4. IDE 适配层

把同一套核心规范转换为不同 IDE 或 Agent 能识别的入口、配置和触发方式。适配层可以变化，但不得改变规范含义。

## 四、核心工作包

### 工作包一：治理规则体系

需要定义治理规则应包含什么、如何组织以及如何判断其有效。

交付物包括：

- 治理规则目录与分层方式；
- 规则条目的规范格式；
- 强制规则、建议规则和说明性内容的区分方式；
- 规则适用范围、例外和冲突处理机制；
- 规则变更和审核流程；
- 面向不同 IDE 的适配方法。

验收重点是规则是否语义明确、边界清晰，是否能被人审核、被 AI 稳定理解，并能映射到检测或交付行为。

### 工作包二：指标与检测体系

需要建立指标列表、阈值设置方法和检测工具。

交付物包括：

- 指标目录及每项指标的质量目的；
- 指标定义、计算口径和采集来源；
- 默认阈值及项目覆盖方式；
- 检测工具和统一执行入口；
- 检测结果格式；
- 失败等级、阻断策略和豁免流程。

阈值不能脱离指标口径单独存在。每个硬性阈值都应说明它保护什么风险，以及误报或漏报时如何处理。

### 工作包三：语义立约规范

需要规范需求迭代文档和代码契约的格式、内容与衔接关系。

需求迭代文档至少应覆盖：

- 背景与目标；
- 本次范围与非目标；
- 角色或使用场景；
- 行为要求和约束；
- 验收条件；
- 风险、假设与待决策项。

代码契约至少应覆盖：

- 对外可观察的实体和职责；
- 输入、输出与错误；
- 状态变化和关键不变量；
- 实体之间的关系；
- 兼容性要求；
- 与需求及检测项的可追溯关系。

具体模板可以随项目类型变化，但不能丢失“可审核、可实现、可验证”三个目标。

### 工作包四：代码交付与检测流程

需要把语义立约之后的实现、检查和验收串成一条明确流程。

建议的标准流程为：

1. 确认需求迭代文档；
2. 建立或更新代码契约；
3. 人审核契约并处理待决策项；
4. AI 按契约实现代码；
5. 执行规则检查、契约一致性检查和指标检测；
6. AI 修复实现偏差并重新检测；
7. 人依据验收条件确认产品结果；
8. 归档本次变更的文档、代码和检测结果。

若发现需求或契约本身错误，应先修正文档，再调整代码，避免以现有实现反向定义正确语义。

## 五、建议的实施顺序

落地时不宜同时铺开所有能力。建议按依赖关系分阶段建设：

1. **统一语言**：先建立术语表，消除核心概念混用。
2. **固定协作接口**：确定需求迭代文档和代码契约的最小模板。
3. **建立基础规则**：先覆盖高频、严重且容易表达的质量风险。
4. **接入基础检测**：为可量化规则提供采集和阻断能力。
5. **跑通一个闭环**：选择一次真实需求验证完整流程。
6. **沉淀操作手册**：把实际步骤、失败模式和处理办法写入手册。
7. **扩展 IDE 适配**：在核心流程稳定后适配更多工具。

## 六、整体验收标准

当以下条件同时满足时，可以认为机制完成了第一阶段落地：

- 一名未参与机制设计的用户能够依据操作手册完成一次需求迭代；
- 核心文档不依赖特定 IDE 也可被读取和审核；
- 同一套核心语义能够通过适配层供至少一种目标 IDE 使用；
- 需求、代码契约、代码和检测项之间可以追溯；
- 关键指标能够自动采集，并按约定阈值给出结果；
- 实现偏离代码契约时，流程能够发现并阻止无说明的交付；
- 文档错误和代码错误有明确、不同的修正路径。

## 七、尚待决策的事项

原文尚不足以确定以下内容，应在后续设计中形成独立决策，而不应在当前阶段默认为既定方案：

- 首批支持哪些 IDE 与 Agent；
- 是否存在足够成熟的通用 Agent 协议，以及是否值得采用；
- 代码契约采用纯文本模板、机器可读结构，还是二者结合；
- 首批指标的具体范围和默认阈值；
- 规则、契约与代码一致性检查能够自动化到什么程度；
- 检测失败时哪些情况必须阻断，哪些情况允许有记录地豁免。
